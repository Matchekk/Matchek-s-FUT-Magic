# FC27 readiness

FC27 behavior is **unknown/unverified** until captured from real, redacted
observations and covered by fixtures and contract tests. The current release is
architecture-ready and observe-only; it does not claim live FC27 planning,
scoring, eligibility, submission, or recovery support.

## Version boundary

`GameContext` carries an explicit `fc26 | fc27 | unknown` value, challenge kind,
version-observation state, and source. The production bridge is a documented
versionless FC26 legacy contract; its sole compatibility default is applied in
the isolated `ControllerAdapter`. Explicit FC27, unknown, malformed, or future
values are never allowed to fall through to FC26.

The runtime propagates that context to the Product Shell and invalidates cached
plans when it changes. Before every version-sensitive WorkflowEngine handler it
reads context again. FC27 or unknown pauses before the EA adapter is called.

## Strategy boundary

The immutable local `GameStrategyRegistry` resolves an exact game-version and
goal pair. Legacy strategies are registered only for FC26. FC27 receives
observe-only descriptors with no strategy function and `canCompileSteps=false`.
The PlanCompiler checks this shipped-code gate before capability preflight or
strategy invocation, and binds strategy identity/readiness/evidence revision
into the immutable plan ID.

An outer caller, injected resolver, compatibility record, or capability list
cannot activate FC27 execution. Executable versions are a closed local-code
allowlist that currently contains FC26 only.

## Separate streamlined model

Classic squad challenges and future streamlined score challenges are separate
domain types. FC27 is never modeled as FC26 with unusual flags and the FC27
contract imports no classic solver or constraint compiler.

The bounded `fc27_streamlined_challenge_observation.v1` model represents:

- target and current score;
- eligibility and rarity rule-set references;
- duplicate and partial-submission support;
- score-model version;
- challenge classification and identity;
- quarantined fingerprints for unmapped evidence.

Every semantic field is `VERIFIED`, `UNVERIFIED`, or `UNKNOWN`. Unknown and
unverified fields keep `value:null`; absence never becomes zero, false, an
empty rule set, or a guessed default. Verified facts require reviewed-fixture
evidence. Live observations alone cannot declare a rule verified.

## Score-provider boundary

`ItemScoreProvider` is an application port with exact bounded request/response
contracts. It accepts random request-local handles and semantic facts, not EA
controllers, DOM objects, credentials, URLs, workflows, or action instructions.
Responses must exactly match the request, model, challenge, expiry, and full
handle set. The shipped `NotConfiguredItemScoreProvider` exposes an immutable
not-configured descriptor and fails with a stable error; it never returns a
plausible zero score.

## Future activation gates

Progression is Review first, Assisted only after verified submission, and Auto
only after dedicated recovery and live compatibility evidence. Activation
requires all of the following in shipped local code:

1. redacted reviewed FC27 fixtures and a matching adapter/build contract;
2. verified challenge classification and all operation-required facts;
3. a verified streamlined strategy and independent score/eligibility models;
4. version-specific capabilities for read, apply, verify, and recovery;
5. local protection validation and exact stale-state fingerprints;
6. persisted submission intent, postcondition verification, and reconciliation;
7. Review-mode end-to-end evidence before any Assisted or Auto expansion.

Remote recipe or compatibility metadata can only downgrade these gates. It
cannot register code, add capabilities, remove required evidence, or upgrade
FC27 readiness.
